## Findings

1. **Blocker — progress sync rejects the live 13-guide catalog.** The client sends every eligible guide to `rpc_sync_user_guide_progress` ([useGuideProgress.ts:57–70](C:/Users/j/Documents/Github/TrustFlow/hooks/useGuideProgress.ts:57)), but the SQL allowlist accepts only six v1 IDs plus `profile` v2 ([migration:102–107](C:/Users/j/Documents/Github/TrustFlow/supabase/migrations/20260920110000_user_guide_progress.sql:102)). The catalog also contains `task-workflow`, `deadlines`, `projects`, `portfolios`, `filehub-sharing`, `team-assignments`, and `intelligence` ([contextualGuides.ts:71–189](C:/Users/j/Documents/Github/TrustFlow/lib/contextualGuides.ts:71)). Because sync validates each submitted guide, a normal user’s payload hits an unsupported ID and the RPC fails; the checklist then reports a progress load error and disables guide launches.

2. **High — the SQL completion-step metadata is stale, so Done writes are rejected.** The registry defines three steps per guide, but the SQL helper reports final step `0` for `profile` and `1` for several other IDs ([migration:102–106](C:/Users/j/Documents/Github/TrustFlow/supabase/migrations/20260920110000_user_guide_progress.sql:102), [contextualGuides.ts:73–188](C:/Users/j/Documents/Github/TrustFlow/lib/contextualGuides.ts:73)). The client submits the registry’s actual last step when completing ([useGuideProgress.ts:125–127](C:/Users/j/Documents/Github/TrustFlow/hooks/useGuideProgress.ts:125)); the RPC rejects steps beyond its stale final-step value or a Done write at the wrong step ([migration:204–214](C:/Users/j/Documents/Github/TrustFlow/supabase/migrations/20260920110000_user_guide_progress.sql:204)). Updating the ID allowlist alone would therefore still leave completion broken.

3. **High — “New” markers ignore the provider’s eligibility-diff result.** The provider computes newly eligible capability guide IDs from an eligibility change ([ContextualGuideContext.tsx:93–116](C:/Users/j/Documents/Github/TrustFlow/contexts/ContextualGuideContext.tsx:93)), but the launcher and checklist instead mark any unacknowledged capability guide as new ([GuideHost.tsx:13–18](C:/Users/j/Documents/Github/TrustFlow/components/guides/GuideHost.tsx:13), [GuideChecklist.tsx:159](C:/Users/j/Documents/Github/TrustFlow/components/guides/GuideChecklist.tsx:159)). This marks initially available guides as newly unlocked. The focused test that expects otherwise currently fails at [GuideHost.test.tsx:176](C:/Users/j/Documents/Github/TrustFlow/components/guides/GuideHost.test.tsx:176).

4. **Medium — the team assignment guide can appear for users without team-management access.** `team-assignments` uses the same `team` shortcut as the directory guide ([contextualGuides.ts:163–168](C:/Users/j/Documents/Github/TrustFlow/lib/contextualGuides.ts:163)). That shortcut is visible with `user.view_all` or `role.manage` ([constants.ts:115](C:/Users/j/Documents/Github/TrustFlow/components/sidebar/constants.ts:115)), while team-management controls are gated on `role.manage` ([_people_adaptive.tsx:124](C:/Users/j/Documents/Github/TrustFlow/components/tabs/_people_adaptive.tsx:124)). A view-only user can therefore see guidance that tells them to update team membership.

5. **Medium — the first-run checklist intro still opens as a blocking popup.** `WelcomeTour` becomes visible whenever `onboarded_at` is empty ([WelcomeTour.tsx:18–46](C:/Users/j/Documents/Github/TrustFlow/components/onboarding/WelcomeTour.tsx:18)) and is mounted in both roots ([native layout](C:/Users/j/Documents/Github/TrustFlow/app/_layout.tsx:297), [web layout](C:/Users/j/Documents/Github/TrustFlow/app/_layout.web.tsx:154)). That conflicts with the stated “no forced tours/nags” requirement, even though individual guides do not auto-open.

## Tests and residual risks

The focused run reported **42 passing and 1 failing test**. The catalog test only checks for at least 12 entries and at least 3 steps per guide ([contextualGuides.test.ts:28–40](C:/Users/j/Documents/Github/TrustFlow/lib/contextualGuides.test.ts:28)), so it does not enforce exactly 13 entries or the accuracy of their content. The SQL contract check syncs only `tasks` and `top-bar` ([check_user_guide_progress.sql:100–105](C:/Users/j/Documents/Github/TrustFlow/supabase/checks/check_user_guide_progress.sql:100)), missing both catalog/allowlist parity and completion-step parity.

The user+workspace persistence key and database primary key are aligned, and both app roots mount one guide provider/host. The checklist panel is scrollable, movable, and has no entrance animation; its lack of animation is reduced-motion safe. I did not drive the UI in a browser or native app, so runtime placement and screen-copy accuracy remain unverified.
